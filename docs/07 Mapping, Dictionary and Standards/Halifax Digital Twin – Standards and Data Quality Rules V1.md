# Standards and data quality rules

Step 12 of the data-design method. 21 Nov 2026\. Draft for the architect's review.

This document states the rules every table in the Halifax Digital Twin follows, and the data quality rules that check them. The rules are drawn from Physical Model V1 (`database/docs/physical-model-v1.md`), Logical Model V1 (`database/generator/logical_model_spec.py`), the demo loaders and `PROJECT_CONTEXT.md` section 13\. Where a rule is still an open question for the architect, it says so.

Each data quality rule has a stable id (`DQ-001` and so on). An id is never reused or renumbered: a retired rule keeps its id and is marked retired. The automated checks in `transform/dbt/` carry the same id as a tag and in their name, so `dbt test --select tag:DQ-044` runs exactly one rule.

## 1\. Naming

| Standard | Rule | Example |
| :---- | :---- | :---- |
| N1 | Physical names are the logical names in snake\_case, word for word | Street Segment becomes `street_segment` |
| N2 | The only abbreviation is Timestamp to `ts` | Event Start Timestamp becomes `event_start_ts` |
| N3 | A column ends with its class word, which tells its type | `_id`, `_code`, `_name`, `_date`, `_ts`, `_amount`, `_count`, `_flag`, `_number` |
| N4 | Constraint prefixes | `pk_` primary key, `ak1_` and `ak2_` alternate keys, `fk_` foreign key, `ck_` check, `ix_` index, `trg_` trigger |
| N5 | Audit columns start with `dw_` | `dw_loaded_ts`, `dw_batch_id` |
| N6 | Names over 63 characters are cut to 56 and given a 6-character fingerprint | PostgreSQL's limit is 63 |
| N7 | Never invent an entity or column name. A name not in the spec is a question for the architect |  |
| N8 | `event_type_code` and `asset_type_code` hold the entity name from the spec | "Trip", "Stop Arrival", "Road Closure", "Building Permit" |
| N9 | New tables go in `gold`, never in `silver`, unless the architect approves a model change |  |

## 2\. Keys

| Standard | Rule |
| :---- | :---- |
| K1 | Kernel entities (`location`, `party`, `asset`, `event`) and `schedule_version`, `scheduled_trip` use a surrogate `bigint` key, `GENERATED BY DEFAULT AS IDENTITY` |
| K2 | A subtype table shares its supertype's key: a Trip is one row in `event` and one in `trip` with the same `event_id` |
| K3 | Reference tables use their own codes as keys: `sector` (S04), `subsector` (TRN-01), `source` (SRC-001), `measure`, `calendar_date` |
| K4 | The source's own key is alternate key 1: `(source_id, source_<entity>_key)`, unique. Loads are idempotent on it: a re-run updates, never duplicates |
| K5 | A source key is stored exactly as the source sends it. Where one source row becomes several silver rows, the key is built with \` |
| K6 | The supertype's discriminator and the subtype row agree: every `event` typed "Trip" has a `trip` row, and every `trip` row's event is typed "Trip" |
| K7 | `vehicle_position` is the one rolled-down event: key `(vehicle_asset_id, position_ts)`, no `event` row |

## 3\. Time

| Standard | Rule |
| :---- | :---- |
| T1 | Every timestamp is `timestamptz`, stored in UTC. The database server runs in UTC |
| T2 | Times are shown in Halifax time (America/Halifax), on the 24-hour clock, with dates written as 21 Nov 2026 |
| T3 | `event_date` is the Halifax calendar date of `event_start_ts`, except for Trip, whose `event_date` is the GTFS service date |
| T4 | The transit service day rolls over at 03:00 Halifax time, not midnight. A trip seen at 01:30 belongs to the previous day's service when the feed gives no start date |
| T5 | GTFS schedule times are `interval`, because they can pass 24:00:00 (25:10:00 is 01:10 the next morning, same service day) |
| T6 | An open end is stored as empty, never as a far-future date. Halifax's "year 3000" alert end is stored as no end |
| T7 | A row is never stamped in the future beyond a 5-minute clock tolerance |

## 4\. History (SCD Type 2\)

| Standard | Rule |
| :---- | :---- |
| H1 | 22 tables keep history: `sector`, `subsector`, `source`, `measure`, `location` and its 6 subtypes, `party`, `organization`, `asset` and its 8 subtypes |
| H2 | The table holds the current version with `valid_from_ts`. The trigger `silver.fn_scd2_capture` copies the old version to `<table>_hist` with `valid_to_ts` on update or delete |
| H3 | `<table>_timeline` shows every version with `valid_from_ts`, `valid_to_ts`, `is_current` |
| H4 | An update that changes nothing real adds no history, so a reload of identical data is free |
| H5 | Write the final row in one statement. A second UPDATE of the same row in one load creates a false version |
| H6 | Versions of one key never overlap and never end before they start |
| H7 | Nothing is deleted. A stop or route missing from a new file is retired with an out-of-service date |
| H8 | Events are not historized in V1: a status change overwrites the status |

## 5\. Geometry

| Standard | Rule |
| :---- | :---- |
| G1 | Geometry is `geometry(Geometry, 4326)` (WGS 84 longitude and latitude). Vehicle positions are `geometry(Point, 4326)`, computed from latitude and longitude |
| G2 | Every geometry is valid (`ST_IsValid`) and not empty |
| G3 | `geometry_type_code` agrees with the stored geometry: Point (point or multipoint), Line (linestring or multilinestring), Polygon (polygon or multipolygon), None (no geometry, for Citywide) |
| G4 | Geometry lies inside the Halifax region envelope, longitude \-64.6 to \-62.0 and latitude 44.3 to 45.4 (a generous box around HRM) |
| G5 | `centroid_latitude` and `centroid_longitude` are filled whenever a geometry is |
| G6 | Coordinates are kept at 6 decimal places (about 10 cm) |
| G7 | ArcGIS sources are requested with `outSR=4326`, so no reprojection happens in the loader |
| G8 | Location rules (Logical Model V1, LOCRULE) say which location subtype an event or asset points to. Foreign keys cannot express them, so DQ-044 and DQ-045 check them |

## 6\. Code values

| Standard | Rule |
| :---- | :---- |
| C1 | Codes are domain valid values (`varchar(30)`), except Sector, Subsector, Source and Measure, which are reference tables |
| C2 | Use the spec's values where it lists them. Where it gives none, the loader's choice is recorded in the source-to-target mapping and becomes a question for the architect |
| C3 | Codes are in sentence case ("Affected route"). GTFS-RT enumerations are stored as the feed's enum names (IN\_TRANSIT\_TO), pending the architect's decision (open question 8\) |

## 7\. Audit and provenance

| Standard | Rule |
| :---- | :---- |
| A1 | Every silver table has `dw_loaded_ts` (when the row was last written) and `dw_batch_id` (which load wrote it). `vehicle_position` has `dw_loaded_ts` only |
| A2 | A loader sets `dw_batch_id` to the `bronze.feed_fetch.fetch_id` of the download it loaded, so every row traces back to one raw file |
| A3 | `source_id` on Location, Party, Asset, Event and Vehicle Position records where each row came from |
| A4 | Every download attempt, success or failure, is one row in `bronze.feed_fetch`. A failure has `error_text`; a success has `file_path` and `file_sha256` |
| A5 | Raw files are kept for a rolling 7 days (decision of 21 Nov 2026); `bronze.feed_fetch` rows are kept for ever |
| A6 | No personal data. Buyer, seller, host and applicant names are not loaded |

## 8\. Data quality rules

Severity: **error** means the data breaks the model and the load or the source must be fixed; **warn** means the data is suspect, or the rule cannot yet be met for a known reason that is written next to it. A warn rule is still reported, never hidden.

### Keys and uniqueness

| Id | Rule | Table | Column | Severity | dbt test |
| :---- | :---- | :---- | :---- | :---- | :---- |
| DQ-001 | Primary key is unique and not empty | `event`, `asset`, `location`, `bronze.feed_fetch` | `event_id`, `asset_id`, `location_id`, `fetch_id` | error | `dq_001_*` (unique, not\_null) |
| DQ-002 | Source key (AK1) is unique | `event`, `asset`, `location` | `(source_id, source_event_key)` and the like | error | `dq_002_*` (unique\_combination) |
| DQ-003 | One arrival per trip and stop sequence | `stop_arrival` | `(trip_event_id, stop_sequence_number)` | error | `dq_003_*` |
| DQ-004 | One trip per scheduled trip and service date (not enforceable by `ak1_trip`; open question 7\) | `trip` \+ `event` | `scheduled_trip_id`, `event_date` | error | `dq_004_*` (singular) |
| DQ-005 | A Trip's source key carries its service date: \`\<trip\_id\> | \<event\_date\>\` | `event` (Trip) | `source_event_key`, `event_date` | error |

| Id | Rule | Table | Column | Severity | dbt check |
| :---- | :---- | :---- | :---- | :---- | :---- |
| DQ-090 | SRC-001 vehicle positions fetched successfully within 2 minutes (error after 10\) | `bronze.feed_fetch` | `fetched_ts` | warn / error | source freshness `feed_fetch_src_001` |
| DQ-091 | SRC-002 trip updates, same thresholds | `bronze.feed_fetch` | `fetched_ts` | warn / error | source freshness `feed_fetch_src_002` |
| DQ-092 | SRC-003 service alerts, same thresholds | `bronze.feed_fetch` | `fetched_ts` | warn / error | source freshness `feed_fetch_src_003` |
| DQ-093 | SRC-015 street closures fetched within 24 hours (error after 72\) | `bronze.feed_fetch` | `fetched_ts` | warn / error | source freshness `feed_fetch_src_015` |
| DQ-094 | SRC-066 building permits fetched within 7 days (error after 31\) | `bronze.feed_fetch` | `fetched_ts` | warn / error | source freshness `feed_fetch_src_066` |
| DQ-095 | Latest vehicle position within 5 minutes (error after 30\) | `vehicle_position` | `position_ts` | warn / error | source freshness `vehicle_position` |
| DQ-096 | Gate 0: no gap over 2 minutes between successful fetches of SRC-001 to 003 in the last 48 hours | `bronze.feed_gap` | `gap` | warn | `dq_096_*` (singular) |
| DQ-097 | A failed fetch records its error | `bronze.feed_fetch` | `error_text` | warn | `dq_097_*` |

The freshness thresholds for SRC-001 to 003 match the serving API's "stale after 2 minutes" rule. The SRC-015 and SRC-066 thresholds are interim, not yet decided: they depend on how often the architect wants the ArcGIS loaders to run.

### Rules already enforced by the database

These hold by construction and are not re-tested: NOT NULL columns, primary and alternate keys other than those above, the 108 foreign keys, and the domain CHECK constraints (percent 0 to 100, latitude and longitude ranges, counts 0 or more except Reported Delay Seconds, years 1700 to 2100, lengths and areas 0 or more, URLs starting with http\:// or https\://). The data dictionary lists each one per column.

## 9\. Running the checks

From `transform/dbt` (first time: see `transform/dbt/README.md`):

```
.\run-quality.ps1                    # dbt test, then dbt source freshness, read-only
.\run-quality.ps1 -Select tag:DQ-044 # one rule
```

The checks open a read-only session (`default_transaction_read_only=on`) and the project has no models, so they cannot change the database.
