# Halifax Digital Twin – Physical Model V1

Step 9 · 20 Nov 2026 · Emmanuel Mbachu

Physical Model V1 turns the 63-entity logical model into a working PostgreSQL 16 \+ PostGIS 3 database that runs on your own computer at no cost. The code lives in the GitHub repository under `database/`. It was tested end to end on a clean database: every script runs, and a smoke test builds a small bus trip, checks the history and foreign keys, then rolls everything back.

## How the logical model became tables

**One table per entity.** Every logical entity is a table in the silver schema with the same name in snake\_case: Street Segment becomes `silver.street_segment`.

**Supertypes and subtypes: one table each (erwin's "Identity" transformation).** Location, Party, Asset and Event each have a table, and every subtype has its own table that shares the supertype's key. A Trip is one row in `event` plus one row in `trip`, both with the same `event_id`. This is the same result whether erwin draws a subtype circle or a plain identifying line.

**One exception, Vehicle Position (rolled down).** A bus reports its position every few seconds. Giving every GPS ping its own row in `event` would make the event table enormous and slow for everything else. So `vehicle_position` stands alone: it carries its own time (`position_ts`) and source (`source_id`), has no `event_id`, and its key is `(vehicle_asset_id, position_ts)`. It still points to `trip`, `vehicle` and `source` through foreign keys.

## Naming rules

| Rule | Example |
| :---- | :---- |
| Lower case, words joined by underscores (snake\_case) | Street Segment → street\_segment |
| Logical name kept word for word, so erwin and SQL match | Parent Area Location ID → parent\_area\_location\_id |
| One abbreviation only: Timestamp → ts | Event Start Timestamp → event\_start\_ts |
| Class word stays at the end and tells you the type | …\_id, …\_code, …\_name, …\_date, …\_ts, …\_amount, …\_count, …\_flag |
| Constraint prefixes | pk\_ primary key, ak1\_/ak2\_ alternate key, fk\_ foreign key, ck\_ check, ix\_ index, trg\_ trigger |
| Audit columns start with dw\_ | dw\_loaded\_ts, dw\_batch\_id |
| Names over 63 characters are cut and given a short fingerprint | PostgreSQL's limit is 63 |

## Keys

- **Surrogate keys generate themselves.** `location`, `party`, `asset`, `event`, `schedule_version` and `scheduled_trip` use `GENERATED BY DEFAULT AS IDENTITY`. The database numbers new rows, but a load can still supply its own number when it needs to. Subtype tables take the key of their supertype row.  
- **Reference tables use their own codes as keys:** `sector` (S04), `subsector` (TRN-01), `source` (SRC-001), `measure`, `calendar_date`.  
- **Alternate keys become UNIQUE constraints.** The source's own key can't be loaded twice. For example `ak1_location` covers `(source_id, source_location_key)`.

## History: SCD Type 2

Charter principle 3 says nothing is overwritten. The 22 tables whose rows can change carry full history:

> sector, subsector, source, measure, location and its 6 subtypes, party, organization, asset and its 8 subtypes

**How it works**

1. Each of these tables holds the **current** version of every row, plus `valid_from_ts`, the time that version became current.  
2. A trigger watches the table. When a row is **updated** or **deleted**, the old version is copied into `<table>_hist` with `valid_to_ts` set to the time it stopped being true.  
3. An update that changes nothing real (only the load time) is ignored, so reloading the same data adds no history.  
4. The view `<table>_timeline` puts both together, so you can read every version in the classic SCD2 shape: `valid_from_ts`, `valid_to_ts`, `is_current`.

**Why a separate history table instead of extra rows in the same table?** Foreign keys need one row per key. If old versions sat in the same table, `asset_id` would no longer be unique, and every foreign key pointing at it would break. Keeping the current row in place and the old versions beside it keeps all 108 foreign keys simple. SQL Server's built-in temporal tables use the same design.

**Not historized in V1:** events. An event records something that happened at a time, so it rarely changes. A status change, such as a 311 request being closed, overwrites the status in V1. Adding history to event tables later uses the same trigger.

## Vehicle positions: partitions

`vehicle_position` is split into one partition per month: `vehicle_position_2026_11`, `vehicle_position_2026_12`, and so on, plus a default partition for anything outside them.

- **Speed:** a query for one day only reads that month's partition. This is called *partition pruning*.  
- **Storage control:** the charter's hybrid storage plan keeps raw positions for a rolling window, then condenses them into stop arrivals. Dropping an old month is one instant statement, `DROP TABLE silver.vehicle_position_2026_11;`, instead of deleting millions of rows.  
- **Adding months:** script 05 creates partitions up to December 2027\. Copy one line to add more.

## Indexes

- **Foreign keys:** PostgreSQL does not index foreign keys on its own. Each foreign-key column set got an index (56 in total), except where the primary key already starts with the same columns.  
- **Spatial:** GiST indexes on `location.location_geometry` and `vehicle_position.position_geom` make "near" and "inside" questions fast.  
- **Time:** `event (event_start_ts)` and `event (event_type_code, event_date)` for questions such as "all trips on a given day".

## Constraints from the domains

Every column using one of these domains gets a CHECK constraint:

| Domain | Rule |
| :---- | :---- |
| Percent | 0 to 100 |
| Latitude | −90 to 90 |
| Longitude | −180 to 180 |
| Count | 0 or more (except Reported Delay Seconds, which can be negative for an early bus) |
| Year | 1700 to 2100 |
| Lengths and areas | 0 or more |
| URL | Starts with http\:// or https\:// |

The location rules (for example, "a Snow Clearing must point to a Street Segment") can't be expressed as foreign keys. They will be data quality checks in step 12\.

## Audit and provenance

- Every silver table has `dw_loaded_ts` (when the row was last written) and `dw_batch_id` (which load wrote it).  
- `source_id` on Location, Asset, Event, Party and Vehicle Position records where each row came from.  
- `bronze.feed_fetch` records every download of a feed. The view `bronze.feed_gap` shows the time between downloads, which is how Gate 0 (48 hours with no gaps) is checked.

## Comments: the dictionary inside the database

Every table and column has a description, stored in the database with `COMMENT ON`. pgAdmin and DBeaver show it next to the data. Column comments name the logical attribute and its domain, for example *"Event Start Timestamp. Domain: Timestamp. UTC"*.

## What differs from the logical model

| Logical model | Physical model | Why |
| :---- | :---- | :---- |
| Vehicle Position is an Event subtype | Stands alone, partitioned by month, key (vehicle, time) | Volume |
| Service Calendar "Monday Flag to Sunday Flag" | Seven boolean columns | One column per weekday |
| Service Day Time stored as text | interval | Lets you do arithmetic on GTFS times, including ones past 24:00 |
| No audit columns | dw\_loaded\_ts, dw\_batch\_id on every table | Provenance (principle 1\) |
| History not drawn | valid\_from\_ts, \_hist tables, \_timeline views | SCD Type 2 (principle 3\) |
| Trip "unique per scheduled trip and service date" | Not enforced yet | The service date lives on `event`, so a cross-table rule goes into the step 12 checks |

## Adding a new sector later

Nothing existing changes. For a sector such as Public Safety:

1. Add its subsectors to `silver.subsector`.  
2. Add its sources to `silver.source`.  
3. Create its event or asset subtype tables, sharing `event_id` or `asset_id`.  
4. Add foreign keys and indexes.  
5. Write their comments.

This is charter principle 4: additive change.
