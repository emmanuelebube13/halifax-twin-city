# Learning note: model deliverables (steps 10 to 12, Phase 2 task 6)

21 Nov 2026. Branch `m01-model-deliverables`.

## What was built and why

| Step | File | What it is | Why |
| --- | --- | --- | --- |
| 11 | `engineering/model/data-dictionary.csv`, `.md` | One row per column: 63 silver tables, 520 columns, plus `bronze.feed_fetch`. Logical name, domain, type, nullability, keys, references, checks, description | A dictionary typed by hand drifts from the model within weeks. This one is generated by `database/generator/build_data_dictionary.py` from the spec and the SQL, and a test fails if the committed files differ from a fresh run |
| 12 | `engineering/model/standards.md` | Naming, keys, time, SCD2, geometry, code value and audit standards, and 56 data quality rules with stable ids (DQ-001 to DQ-098), each with its table, column and severity | Rules written down once, with an id, can be tested, discussed and changed one at a time |
| Phase 2 task 6 | `transform/dbt/` | dbt Core project with no models: 94 tests and 6 freshness checks over bronze and silver, each named and tagged with its rule id | Automated checks that run in seconds, every time, against the real data. Read-only by design |
| 10 | `engineering/model/sttm.csv`, `sttm.md` | 143 mapping rows for SRC-001 to 004, 015 and 066, from the loaders workstreams B and C committed | The bridge between the source inventory and the model: for every silver column, where it comes from and how |

Two ideas worth keeping:

- **Generated documents.** The dictionary is a build output, like compiled code. Never edit it; change the spec or the SQL and regenerate. `--check` is what a CI pipeline would run.
- **A failing rule is a finding.** The first run found real problems: one road closure that ends before it starts (DQ-060), arrival dates not updated past midnight (DQ-061, a one-line loader fix), and the feed's stop sequence disagreeing with the schedule for about 18 per cent of arrivals (DQ-043). None was loosened to make the run green.

## How to run it

Data dictionary, from the repository root:

```powershell
py -3.12 database\generator\build_data_dictionary.py           # regenerate
py -3.12 database\generator\build_data_dictionary.py --check   # confirm up to date
py -3.12 -m unittest discover -s database\generator\tests -v
```

Data quality checks (first time: `py -3.12 -m venv .venv`, `.venv\Scripts\python -m pip install -r requirements.txt`, copy `profiles.example.yml` to `profiles.yml`):

```powershell
cd transform\dbt
.\run-quality.ps1                       # all tests, then freshness
.\run-quality.ps1 -Select tag:DQ-060    # one rule
.venv\Scripts\python -m unittest test_rule_coverage -v
```

The profile has an empty password, so libpq reads `pgpass.conf` itself, and the runner sets `PGOPTIONS=-c default_transaction_read_only=on`, so even a mistaken test could not write.

## Hands-on exercise

1. Run `.\run-quality.ps1 -Select tag:DQ-060`. It fails with 1 result.
2. Open `target\compiled\halifax_twin_quality\models\silver_sources.yml\dq_060_event_end_not_before_start.sql`: this is the exact SQL dbt ran. Paste it into pgAdmin and add `select event_id, source_event_key, event_start_ts, event_end_ts` to see the row.
3. Look the `source_event_key` (a GLOBALID) up in the raw closure file under `C:\halifax-twin-data\bronze\SRC-015\` and decide: is the source wrong, or the loader's time repair? Write your answer as one line in the rule's notes.
4. Add a rule of your own, for example "a building permit's construction value is not negative": give it the next free id (DQ-066) in `standards.md`, add an `expression_is_true` test in `models/silver_sources.yml` named `dq_066_...` with tag `DQ-066`, and run `test_rule_coverage` to see it pass only when both are in place.

## Enterprise mapping

Data dictionary and STTM: DAMA-DMBOK metadata management (CDMP Data Management Fundamentals); data quality rules and automated testing: dbt Core tests and source freshness (dbt Analytics Engineering certification), the same idea as Great Expectations or Informatica Data Quality.
