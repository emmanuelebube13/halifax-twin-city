# Halifax Digital Twin – Learning Notes: from Logical to Physical

Companion to Physical Model V1 · 20 Nov 2026

This guide covers ten ideas, each explained in plain words with a query you can run. Run the queries in psql, pgAdmin or DBeaver, connected to the `halifax_twin` database after `run_all.sql`. Anything that changes data is wrapped in `BEGIN … ROLLBACK`, so your database stays clean.

## 1. Logical vs physical

**Idea.** The logical model says *what* the city's data is: entities, attributes and relationships. It doesn't depend on any database. The physical model says *how one database stores it*: names, data types, indexes, partitions and history. One logical model could have several physical models, such as PostgreSQL today and Databricks later.

**Try it.** List the layers and how many tables each holds.
```sql
SELECT table_schema, count(*) AS tables
  FROM information_schema.tables
 WHERE table_schema IN ('bronze', 'silver', 'gold')
 GROUP BY table_schema ORDER BY table_schema;
```
You'll see bronze and silver; gold appears once its first star schema is built. Silver counts include the history tables and monthly partitions.

## 2. Naming: logical name to physical name

**Idea.** The logical name `Parent Area Location ID` becomes `parent_area_location_id`: lower case, underscores, same words. Keeping the words identical means anyone can trace a column back to the erwin model. In psql, `\d` shows a table's columns, keys and constraints.

**Try it.**
```sql
\d silver.street_segment
```
Look for the role names from erwin: `street_location_id`, `from_intersection_location_id` and `to_intersection_location_id`.

## 3. Surrogate keys and identity columns

**Idea.** A surrogate key is a meaningless number the database assigns, such as `location_id = 1, 2, 3 …`. The source's own key (a GTFS `stop_id`, a permit number) is kept as an *alternate key*, so two sources can never clash. `GENERATED BY DEFAULT AS IDENTITY` means the database numbers rows unless a load supplies its own number.

**Try it.** See which columns are identity columns.
```sql
SELECT table_name, column_name
  FROM information_schema.columns
 WHERE table_schema = 'silver' AND is_identity = 'YES'
   AND table_name NOT LIKE '%\_hist'   -- history tables number their own versions too
 ORDER BY table_name;
```

## 4. Supertypes and subtypes as tables

**Idea.** A Trip is an Event. In the database that's two rows sharing one key: the general facts (when, where, which source) go in `event`, and the trip-specific facts (route, vehicle, status) go in `trip`. To read a whole trip, you join them on `event_id`. That join is what the erwin subtype circle means.

**Try it.** The shape of the join (it returns no rows until data is loaded):
```sql
SELECT e.event_id, e.event_start_ts, e.source_id, t.route_asset_id, t.trip_schedule_status_code
  FROM silver.event e
  JOIN silver.trip  t ON t.event_id = e.event_id
 WHERE e.event_date = date '2026-11-20';
```

## 5. Foreign keys, and why they get indexes

**Idea.** A foreign key stops a row from pointing at something that doesn't exist, such as an arrival for a trip that was never loaded. PostgreSQL checks this automatically, but it does **not** index foreign keys by itself. Without an index, joins and deletes on big tables slow down. That's why script 03 creates 56 indexes.

**Try it.** Try to break a rule. The database refuses.
```sql
BEGIN;
INSERT INTO silver.subsector (subsector_id, sector_id, subsector_name)
VALUES ('XXX-01', 'S99', 'A sector that does not exist');
ROLLBACK;
-- ERROR: violates foreign key constraint ... Key (sector_id)=(S99) is not present in table "sector".
```

## 6. SCD Type 2: keeping history

**Idea.** "Slowly changing dimension Type 2" means that when something changes, you keep the old version with the dates it was true, instead of overwriting it. Here, the current row stays in its table and older versions are copied to `<table>_hist` by a trigger. `<table>_timeline` shows all versions.

**Try it.** Change a source's name, then read its history.
```sql
BEGIN;
UPDATE silver.source SET dataset_name = 'GTFS-RT Vehicle Positions (renamed test)' WHERE source_id = 'SRC-001';
SELECT dataset_name, valid_from_ts, valid_to_ts, is_current
  FROM silver.source_timeline WHERE source_id = 'SRC-001' ORDER BY valid_from_ts;
ROLLBACK;
```
You'll see two rows: the old name, closed (`is_current = false`), and the new name, current.

## 7. Partitioning

**Idea.** A very big table can be split into smaller tables by a range, here one per month. Queries for one day only read one month (*partition pruning*), and an old month can be removed in an instant with `DROP TABLE`.

**Try it.** Ask PostgreSQL how it would run a one-day query. Only the November 2026 partition appears in the plan.
```sql
EXPLAIN
SELECT count(*) FROM silver.vehicle_position
 WHERE position_ts >= '2026-11-20' AND position_ts < '2026-11-21';
```

## 8. PostGIS and SRID 4326

**Idea.** PostGIS adds a `geometry` type and spatial functions. SRID 4326 means "GPS latitude and longitude" (WGS 84). For distances in metres, cast to `geography`. `vehicle_position.position_geom` is a *generated column*: the database builds the point from latitude and longitude by itself, so the two can never disagree.

**Try it.** Distance in metres from Scotia Square to Halifax Ferry Terminal, then whether it's within a 5-minute walk (400 m).
```sql
SELECT round(ST_Distance(
         ST_SetSRID(ST_MakePoint(-63.5752, 44.6488), 4326)::geography,
         ST_SetSRID(ST_MakePoint(-63.5713, 44.6471), 4326)::geography)) AS metres,
       ST_DWithin(
         ST_SetSRID(ST_MakePoint(-63.5752, 44.6488), 4326)::geography,
         ST_SetSRID(ST_MakePoint(-63.5713, 44.6471), 4326)::geography, 400) AS within_400_m;
```
The coordinates are approximate.

## 9. CHECK constraints from domains

**Idea.** A domain in erwin (Latitude, Percent, Count) becomes a rule on every column that uses it. Bad data is stopped at the door instead of being found later in a dashboard.

**Try it.** A latitude of 144 is impossible.
```sql
BEGIN;
INSERT INTO silver.location (location_type_code, geometry_type_code, centroid_latitude, source_id, source_location_key)
VALUES ('Point', 'Point', 144.0, 'SRC-005', 'bad-latitude-test');
ROLLBACK;
-- ERROR: violates check constraint "ck_location_centroid_latitude"
```

## 10. The data dictionary lives in the database

**Idea.** `COMMENT ON` stores a description with each table and column. pgAdmin and DBeaver show it, and you can query it. That's the start of step 11, the data dictionary.

**Try it.**
```sql
SELECT a.attname AS column_name, col_description(a.attrelid, a.attnum) AS description
  FROM pg_attribute a
 WHERE a.attrelid = 'silver.trip'::regclass AND a.attnum > 0 AND NOT a.attisdropped
 ORDER BY a.attnum;
```
